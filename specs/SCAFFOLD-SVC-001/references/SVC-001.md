# User Management Service

## C3 — Summary

C3 component diagram for SVC-001 User Management Service, detailing controllers, application and domain services, repositories, integration adapters, and cross-cutting components handling registration, verification, secure login, session management, logging, and account deletion.

## C3 — Insights

- The service cleanly separates HTTP concerns (HTTP API Layer and controllers) from business workflows (application services) and domain rules (password, policy, and verification services).
- Security requirements from stories (password hashing, HTTPS, verified-only access, lockout and suspension) are encapsulated in dedicated components such as Password Hashing Service, Auth Policy & Lockout Service, and Authorization & Security Filter.
- Registration and OTP flows are split into Registration Application Service and OTP Verification Application Service, aligning with stories that treat OTP generation and verification as distinct responsibilities.
- Session Management Service and Session Repository support inactivity-based session expiration without leaking session logic into controllers, matching the session timeout acceptance criteria.
- Audit Logging Component and Audit Log Repository ensure all login attempts and account lifecycle changes are persisted for security monitoring and traceability.
- External integrations (PostgreSQL, SMTP Email Service, and Auth/Event Stream) are abstracted via repositories and adapters, allowing the User Management Service to evolve from monolith to microservices without major changes to core logic.
- Account Lifecycle Service centralizes account deletion and notification logic to ensure irreversible removal and communication, satisfying the strong deletion requirements.

## API specification — Endpoints

### POST /api/v1/users/registration
Creates a new user account in UNVERIFIED status. Ensures email uniqueness, securely hashes the password, generates a time-limited OTP (5 minutes), persists it, and sends it via email.

### POST /api/v1/users/registration/otp/resend
Generates and sends a fresh OTP for an existing unverified user whose previous OTP is expired or lost. Respects OTP expiry rules and rate-limits resends (implementation-specific).

### POST /api/v1/users/registration/otp/verify
Validates the submitted OTP for the given email. If correct and not expired (within 5 minutes of generation), marks the user as VERIFIED and clears or invalidates the OTP. Otherwise returns appropriate errors (incorrect, expired, or user not found).

### POST /api/v1/auth/login
Authenticates a user with email and password. Only VERIFIED and not SUSPENDED users can log in. Passwords are verified using a secure hashing algorithm. Logs all login attempts (success and failure) with timestamp, user id (where resolvable), and reason for failure. Suspends the account after 3 consecutive failed attempts. Returns an access token and refresh token. Denies access for unverified, suspended, and deleted users with appropriate error messages.

### POST /api/v1/auth/refresh
Issues a new short-lived access token when provided with a valid refresh token. Ensures the user account is still active (not deleted, not suspended).

### GET /api/v1/users/me
Returns basic account information of the authenticated user, including verification and suspension status. Requires a valid access token. Session expiration is enforced via access token expiry (e.g., 15 minutes of inactivity).

### DELETE /api/v1/users/me
Allows a logged-in user to permanently delete their account. Removes user data from the system (subject to implementation and regulatory constraints), revokes access tokens, and sends a confirmation email. Subsequent login attempts must be rejected with a clear notification that the account does not exist.

### GET /health
Returns basic health status for orchestration and monitoring. Does not require authentication.

### GET /api/v1/info
Provides basic metadata about the User Management Service such as version, environment, and build timestamp. Useful for diagnostics and client compatibility checks.


## API specification — Summary

User Management Service API focused on email-based registration, OTP verification, secure login (with logging and account suspension), token-based session handling, and self-service account deletion. The design strictly reflects the supplied features and user stories without adding speculative capabilities.

## API specification — Insights

- The API surface is intentionally narrow: it only exposes the operations mandated by user stories—registration, OTP verification, login, token refresh, self-profile retrieval, and account deletion—plus minimal system endpoints.
- Account lifecycle is modeled explicitly through the User.status field (UNVERIFIED, VERIFIED, SUSPENDED, DELETED), enabling clear business rules for login eligibility, OTP flows, and deletion behavior without extra endpoints.
- Session expiration after inactivity is implemented via short-lived JWT access tokens (e.g., 15 minutes) instead of server-side session state, aligning with the stateless REST constraint while fulfilling the session timeout requirement.
- Login security relies on two complementary mechanisms: per-user failedLoginAttempts leading to SUSPENDED status after three consecutive failures, and generic rate limiting per IP/user to mitigate brute-force attacks.
- OTP flows are fully captured with models and endpoints for initial generation on registration, verification, and optional resend; OTP expiry handling uses HTTP 410 with a dedicated OTP_EXPIRED application error code to make client reactions explicit.
- Auditing requirements for login attempts are satisfied by the LoginAttemptLog model, intended for internal persistence; the stories do not require any public reporting or log-query endpoints, so none are defined.
- Account deletion is constrained to the authenticated user via /api/v1/users/me DELETE, ensuring there is no speculative administrative API or multi-tenant management functionality beyond the scope.
- Error handling is standardized through a single ErrorResponse schema with application-level codes, enabling frontends to branch on stable error codes (e.g., USER_NOT_VERIFIED vs ACCOUNT_SUSPENDED) while keeping HTTP status semantics conventional.
- The design omits advanced concerns like MFA, OAuth2 scopes, HATEOAS links, and field-level authorization because they are not present in the given requirements, keeping implementation simpler and more maintainable for the initial release.
- OpenAPI 3.0.3 is used with a single bearerAuth scheme to match the JWT-based model; this clean separation between access and refresh tokens should map straightforwardly to Spring Boot (Java) security filters in the suggested technology stack.

## API specification — Error handling

- Use standard HTTP status codes: 200 for success, 201 for created resources, 400 for validation errors, 401 for authentication failures, 403 for access to suspended accounts, 404 for unknown users, 409 for conflicts like duplicate email or already verified, 410 for deleted accounts or expired OTPs, and 500 for unexpected server errors.
- All error responses must follow the ErrorResponse schema with fields: timestamp (ISO 8601), status (HTTP code), error (HTTP reason phrase), code (stable application error code like EMAIL_ALREADY_IN_USE, INVALID_OTP, USER_NOT_VERIFIED, ACCOUNT_SUSPENDED, ACCOUNT_DELETED, OTP_EXPIRED, INVALID_CREDENTIALS), message (localized human-readable text), details (optional object, typically a ValidationErrorDetails instance for 400), and traceId (optional correlation identifier).
- Validation errors (HTTP 400) should populate details.fieldErrors with one entry per invalid field, specifying field, message, and optionally rejectedValue, to support precise client feedback for registration, login, and OTP endpoints.
- Login failure scenarios must use specific error codes and messages: INVALID_CREDENTIALS for wrong password; USER_NOT_VERIFIED when credentials are correct but status is UNVERIFIED; ACCOUNT_SUSPENDED when status is SUSPENDED (after three failed attempts); ACCOUNT_DELETED when status is DELETED; USER_NOT_FOUND when the email does not correspond to any user. Each failed attempt must be logged via LoginAttemptLog.
- OTP-related errors should use INVALID_OTP for incorrect codes (HTTP 401) and OTP_EXPIRED for expired codes (HTTP 410). When OTP_EXPIRED occurs, the error message should instruct the user to request a new OTP via the resend endpoint.
- Account deletion conflicts should use ACCOUNT_ALREADY_DELETED with HTTP 410 when a deletion is requested for an already deleted account. Subsequent login attempts should be treated as USER_NOT_FOUND or ACCOUNT_DELETED with a clear message that the account does not exist.
- System endpoints (/health, /api/v1/info) must avoid exposing stack traces or internal error details; on failure they should still conform to ErrorResponse but with a generic message and without sensitive implementation details.
